# SLEKE Custom Downloads Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give each requested APK installation one durable operation owner, a validated artifact and a controlled preferred-installer handoff.

**Architecture:** WorkManager owns execution, a library journal owns durable custom-operation state, and the app maps validated artifacts into existing installers. UI collection is read-only. Platform submission is reconciled before any retry.

**Tech Stack:** Kotlin, WorkManager, Ktor, Android PackageManager/FileProvider/AtomicFile, Hilt and the current seven Aurora installer implementations.

**Spec:** [Approved design](../../specs/2026-10-16-sleke-module-refactor-design.md), section 7; all ten OpenSpec `custom-apk-downloads` requirements.

## Global Constraints

Apply the [coordinator](../2026-10-16-sleke-module-refactor-plan.md). Preserve `:app → :sleke`, `com.sleke.store`, 76 / `4.8.4`, minimum SDK 26 and database 13. Continue requested installs, support newer APK updates and use the preferred installer for manual retries. Cancel/purge unsubmitted enterprise work on confirmed access loss. Never auto-uninstall, silently replay an unknown external handoff, add a certificate policy or change the Room schema.

## Review Focus

D1/D4 cover retained work across identities; D3 covers foreign splits and crash ambiguity; D4 covers access ending at each handoff boundary and membership outage while an artifact is ready. Device tests, not mocks, establish platform acceptance.

## Task D1: Operation, artifact and installer contracts

**Files:**
- Create: `sleke/src/main/java/com/sleke/library/downloads/domain/CustomDownloadRequest.kt`, `DownloadState.kt`, `ValidatedApk.kt`, `CustomDownloadCoordinator.kt`, `ApkInstallGateway.kt`, `InstalledPackageSource.kt`, `InstallAttemptRecorder.kt`.
- Create: `sleke/src/main/java/com/sleke/library/downloads/domain/DownloadTransitionPolicy.kt`.
- Create: `sleke/src/test/java/com/sleke/library/downloads/domain/DownloadTransitionPolicyTest.kt`.

**Interfaces:** `DownloadHandle(value: String)` identifies the actual WorkManager request UUID without exposing WorkManager. `DownloadOwner` is `Public` or `Enterprise(uid: String, enterpriseId: String)`; it is derived from current session state inside the coordinator, never accepted as caller-granted authorization. `CustomDownloadRequest(packageName: String, downloadUrl: String, scope: CatalogScope)` consumes C1. Persist a separate random operation generation; late completions must match handle and generation.

`DownloadState` variants: `Queued`, `Downloading(percent: Int?)`, `Ready`, `AwaitingAccess`, `Submitting`, `PendingConfirmation`, `Installing`, `Installed`, `AlreadyCurrent`, `Failed(reason: DownloadFailure)`, `Cancelled`, `NeedsReconciliation`. Only the final installed/already-current/failed/cancelled states end an observation; pending confirmation/access remains resumable. `DownloadFailure` distinguishes transfer, validation, staging, denied/rejected installation and unavailable recovery evidence; display strings are presentation-owned.

`ValidatedApk(reference: String, packageName: String, versionCode: Long, targetSdk: Int)` has an opaque artifact reference, never a public path/URI. `InstalledPackageSource.versionCode(packageName: String): Long?` is suspending. `InstallReceipt(kind: String, reference: String)` is opaque to library domain. `InstallSubmission` is `Accepted(receipt)`, `Completed`, `Rejected(reason)`, `Unknown`; `InstallReconciliation` is `Pending`, `Installed`, `Failed`, `NotSubmitted`, `Unknown`; `InstallCancellation` is `Cancelled`, `Unsupported`, `AlreadyFinished`.

`ApkInstallGateway` has suspending `submit(handle: DownloadHandle, apk: ValidatedApk): InstallSubmission`, `reconcile(handle: DownloadHandle): InstallReconciliation`, `cancel(handle: DownloadHandle): InstallCancellation`. `InstallAttemptRecorder.prepared(handle, receipt)` and `accepted(handle, receipt)` are synchronous durable writes called on IO before and after a side effect, so a platform callback cannot outrun receipt persistence. The journal serializes these writes with its other mutations. The host resolves artifact references through a data-only `ValidatedArtifactStore` in D2.

`CustomDownloadCoordinator` has suspending `start(request): DownloadHandle`, `retryInstall(handle): DownloadHandle`, `cancel(handle)`, `cancelEnterpriseWork()`, and `observe(handle): Flow<DownloadState>`. A retry may return a new actual handle; callers replace the previous observation only after receiving it. Observation does not execute work.

**Interfaces:** `CustomDownloadJournal` implements D1's recorder and exposes suspending `read(handle): OperationRecord?`, `write(record)`, `records(): List<OperationRecord>`, `remove(handle)`, plus `observe(handle): Flow<DownloadState>`. `OperationRecord` contains format version 1, actual handle, random generation, request, derived owner, phase, validated artifact metadata and prepared/accepted receipt. A successful atomic write precedes the corresponding external handoff. This is custom-operation storage, not a Room migration or metadata cache.

`ValidatedArtifactStore` resolves opaque references inside its owned root; only validated files receive a usable reference. `ApkArchiveReader.read(file: File): ArchiveMetadata?` is data-only; `ArchiveMetadata(packageName, versionCode, targetSdk)` is implemented through PackageManager and faked for JVM tests. `ApkTransfer.fetch(request: CustomDownloadRequest, handle: DownloadHandle, onProgress: suspend (Int?) -> Unit): ValidatedApk` is suspending and owns HTTP, files and validation. The worker consumes these data services and D3's domain gateway when bound in D4.

Missing content length uses indeterminate progress; progress must remain 0–100 when length exists. Cancellation is thrown, not returned as a successful fallback.

**Interfaces:** Consumes D1/D2. Persist callback records before commit/launch and immediately after known acceptance; synchronous callbacks execute on the adapter's IO context; receiver hooks use `goAsync` plus owned IO work and finish their pending result.

**Interfaces:** Implements D1. `CustomDownloadScheduler` is a data-only seam for suspending `findActive(uniqueName)`, `enqueueAndResolve(request, owner): DownloadHandle`, `cancel(handle)` and `states(handle)`. Production uses WorkManager; fake it in JVM tests. Unique name is `sleke:apk:<packageName>`. Identity/owner mismatch is cancelled and invalidated before a new request is accepted. Workers and recovery write the journal; `observe` only reads it and releases its collector after a terminal state.
